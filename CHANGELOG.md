# Changelog

Все заметные изменения проекта документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
проект придерживается [семантического версионирования](https://semver.org/lang/ru/).

## [1.4.1] — 2026-08-19

### Исправлено

- `credentials.json` записывается атомарно: содержимое уходит во временный файл
  в том же каталоге (права `0600` с момента создания) и подменяет целевой через
  `rename`. Обрыв посреди записи больше не может оставить усечённый файл —
  а он читался как «не подключено» и требовал входа заново.
- Ответ Яндекса на refresh без нового `refresh_token` больше не затирает
  сохранённый: старый токен остаётся в файле, и следующий refresh по-прежнему
  возможен. Раньше такой ответ молча превращал вход в «работает до первого
  истечения».
- `finish_login` отвечает честно, когда токен уже сохранён, а проверочный вызов
  к API не удался (например, сеть моргнула): это успешный ответ с предупреждением,
  а не `isError` — вход не нужно проходить заново. Ошибка обмена кода, как и
  раньше, остаётся ошибкой.
- Из authorize-ссылки убран неиспользуемый параметр `state`: в флоу нет редиректа,
  к которому его можно было бы привязать, — код пользователь переносит руками,
  а подмену обмена исключает PKCE.

## [1.4.0] — 2026-08-14

### Добавлено

- Подключение прямо из диалога, без правки конфигурации и без перезапуска клиента:
  `start_login` выдаёт ссылку на Яндекс OAuth, `finish_login` меняет код подтверждения
  на токен и сразу проверяет его живым запросом. Дополняют пару `auth_status`
  (откуда взят токен, когда истекает, где лежит файл) и `logout`.
- Схема входа — OAuth с PKCE (S256) и `redirect_uri=https://oauth.yandex.ru/verification_code`.
  `code_verifier` не покидает процесс, поэтому в переписку попадает только одноразовый
  код, живущий 10 минут: без верификатора он бесполезен, в отличие от самого токена,
  который действует год. Секрет приложения не используется вовсе — сервер работает как
  публичный клиент, и класть `client_secret` в npm-пакет не требуется.
- Токен хранится в `~/.config/mcp-yandex-metrica/credentials.json` с правами `0600`,
  вместе с `refresh_token`: истёкший доступ переоформляется молча, в том числе после
  ответа 401/403 `invalid_token` от API. Раньше токен жил около года и потом ломался
  без объяснений.
- Запрос прав сужен явно: `scope=metrika:read` и `force_confirm=yes`. Без `scope`
  Яндекс выдаёт токен со всеми правами приложения, а `force_confirm` не даёт вернуть
  ранее выданный токен с более широким набором.
- Переменная `YANDEX_METRIKA_OAUTH_CLIENT_ID` — вход через своё OAuth-приложение.
- Событие телеметрии `unconfigured_start`: сервер без токена теперь доживает до
  MCP-хендшейка, поэтому впервые видно, из какого клиента приходят такие установки.

### Изменено

- **Сервер больше не завершается из-за конфигурации.** Отсутствующий токен — рабочее
  состояние: сервер стартует, отдаёт полный список инструментов и объясняет, что делать.
  Прежнее поведение (`process.exit(1)` до хендшейка) оставляло пользователя с молчащим
  сервером: клиент показывал сбой подключения, причина не доходила ни до пользователя,
  ни до модели, и такие установки почти никогда не доживали до первого вызова инструмента.
- `YANDEX_METRIKA_TOKEN` стала необязательной. Заданная — по-прежнему имеет приоритет
  над сохранённым входом; сервер такой токен не обновляет и не удаляет.
- Токен резолвится на каждом запросе, а не кешируется в клиенте — это то, что
  позволяет `finish_login` подействовать в текущей сессии.

### Исправлено

- Ошибка «нет токена» больше не принимается за сетевой сбой: раньше она попадала в
  ветку ретраев и вызов висел несколько секунд на бэкоффе, прежде чем показать
  единственное полезное сообщение.
- Неверный или просроченный код подтверждения объясняется по-человечески. Яндекс
  отвечает на него `bad_verification_code`, а не `invalid_grant` из спецификации
  OAuth, поэтому самый вероятный сбой всего флоу — код живёт 10 минут — возвращал
  сырое «Invalid code» без слова о том, что нужен свежий код через `start_login`.

## [1.3.2] — 2026-08-12

### Добавлено

- Инструкции сервера. В ответе MCP `initialize` теперь едет короткая справка для вызывающей
  модели: чем этот API является и чем не является, чего он не умеет, а также квоты, правила
  повторов и обманчивые ошибки, влияющие на то, как им пользоваться. Раньше это знание жило
  только в README, который модель не читает.
- Полная русификация текстов, которые видит пользователь: описания инструментов и их параметров,
  сообщения об ошибках, справка в ответе `initialize`, README и `docs/TOOLS.md`. Имена инструментов,
  параметров, полей ответа, значения перечислений и переменные окружения остались латиницей.

## [1.3.0] — 2026-08-07

### Добавлено
- Событие телеметрии `startup_failed`: сервер, умирающий из-за отсутствующих
  credentials, сообщает об этом до выхода — с машинным кодом причины
  (`missing_token`, `invalid_counter_id`). Раньше такие установки не
  попадали в телеметрию вовсе:
  процесс завершался раньше MCP-хендшейка, и «не смог настроить» было
  неотличимо от «поставил и не пользуется». Отправляется только код —
  ни имя, ни значение переменной окружения; отключение прежнее:
  `ASKADS_TELEMETRY=0`.

### Изменено
- Конфигурация бросает `ConfigError` вместо немедленного `process.exit`, чтобы
  точка входа успела отправить пинг. Сообщение об ошибке и код возврата для
  пользователя не изменились; ожидание отправки ограничено прежними 2 с.

## [1.2.0] — 2026-08-05

### Добавлено
- Анонимная телеметрия использования: события `server_start` и `tool_call`
  (имя тула, версии пакета/Node/ОС, clientInfo из MCP initialize) на
  `usage.gistrec.cloud`. Токен, данные аккаунта, аргументы вызовов и промпты
  не отправляются; fire-and-forget с таймаутом 2 с. Отключение для всех
  MCP-серверов Ask Ads разом: `ASKADS_TELEMETRY=0` (подробности —
  docs/DEVELOPMENT.md).

### Изменено
- README: npx-команды с `@latest` — npx с закешированным пакетом не проверяет
  реестр, установки без тега оставались на версии момента установки.


## [1.1.0] — 2026-07-02

### Безопасность
- SSRF-гард в HTTP-клиенте: `raw_request` с абсолютным или протокол-относительным
  путём (`https://…`, `http://…`, `\\host/…`) теперь отклоняется — запрос с
  OAuth-токеном не может уйти на чужой хост.

### Исправлено
- Ретрай `5xx` только для идемпотентных запросов (`GET`); `POST`/`DELETE` больше не
  повторяются на `5xx` (исключён риск дубля записи). `429` по-прежнему ретраится
  для любого метода — запрос не был обработан.
- `accuracy` в `get_statistics` принимает число `0..1` или строку (`full`), а не
  только строку — числовой ввод модели больше не падает на валидации.
- Таймаут запроса покрывает и чтение тела ответа (`res.text()` внутри охраняемой
  зоны), а не только заголовки — «медленное» тело больше не висит после таймера.
- Синхронизированы версии `server.json` (root + package) с `package.json`/npm (1.0.3);
  дрейф версий теперь ловит `prepublishOnly` (проверка `check:version`).

### Добавлено
- Ретрай сетевых ошибок/таймаутов для идемпотентных `GET` (ECONNRESET, DNS,
  AbortError); не-`GET` не ретраятся.
- Жёсткие лимиты авто-пагинации `get_statistics`: cap по строкам/байтам
  (`STAT_MAX_ROWS`/`STAT_MAX_BYTES`) и параметр `maxPages` у тула — при упоре
  выставляется `_truncated`/`_truncatedNote`.
- Лимит одной страницы тула снижен до `MAX_TOOL_LIMIT` (10000); полный экспорт —
  через `autoPaginate` (пагинация на `STAT_PAGE_LIMIT`).
- `server.json`: env-переменные `YANDEX_METRIKA_API_BASE` / `TIMEOUT_MS` /
  `MAX_RETRIES` (необязательные, со значениями по умолчанию).
- Тесты: SSRF-гард, метод-зависимые ретраи, сетевые ретраи, cap авто-пагинации,
  `raw_request` confirmWrite-гейт (`raw.test.ts`), аннотации тулов
  (`annotations.test.ts`), схема `accuracy`/`limit`.

### Изменено
- `resolveCounter` вынесен в `tools/util.ts` и используется в `counters`/`statistics`.
- `smoke` печатает только агрегат (число счётчиков) — сырой JSON аккаунта в
  публичные логи CI не попадает; полный вывод за флагом `SMOKE_VERBOSE`.
- Документация: минимальная версия Node приведена к 20+ (соответствует
  `engines`/CI-матрице 20/22/24).

## [1.0.3] — 2026-06-30

### Изменено
- Аннотации read-only тулов: явно проставлены `destructiveHint: false` и
  `idempotentHint: true` (некоторые клиенты, напр. OpenAI Apps review, требуют все
  четыре хинта на каждом туле).

## [1.0.2] — 2026-06-30

### Исправлено
- `metrikaDate` сделан фабрикой — поля дат (`date1`/`date2`) инлайнятся в схему
  вместо `$ref`-дедупликации, которую часть потребителей схемы не разыменовывает.

### Изменено
- CI: least-privilege `permissions` + `concurrency`; матрица Node 20/22/24.
- Документация: значок Glama в README, полный чеклист релиза в CLAUDE.md.

## [1.0.1] — 2026-06-29

### Изменено
- Заголовок в реестре (`server.json`) унифицирован с H1 README — «Yandex Metrica MCP».
- CI: добавлен `health.yml` — ежедневный read-only smoke против реального API Метрики.
- Добавлен `glama.json` для листинга на Glama.

## [1.0.0] — 2026-06-27

### Добавлено
- Первый релиз. MCP-сервер для Yandex Metrica (read-only MVP):
  - `list_counters` и `list_goals` — Management API (счётчики и цели/конверсии);
  - `get_statistics` — Reporting API (`stat/v1/data`): метрики/измерения/период/фильтры,
    сортировка, `accuracy`, авто-пагинация (`getAllStat`), проброс `totals` и флага
    `sampled`/`sample_share`;
  - `raw_request` — escape hatch на любой путь API (`management/v1/...` или `stat/v1/data`);
    GET свободно, POST/DELETE — только с `confirmWrite=true`.
- OAuth-токен (scope `metrika:read`), ретраи на 429/5xx с бэкоффом, таймаут запроса,
  `counterId` с дефолтом из `YANDEX_METRIKA_COUNTER_ID`.
